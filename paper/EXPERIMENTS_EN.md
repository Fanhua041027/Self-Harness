# 4 Experiments

> This section follows the protocol in `Self-Harness.pdf`, but the repository currently completes only a validity audit of the historical Clean64 pipeline, not an interpretable surrogate-model effect reproduction. The fixed-denominator values are neither a direct replication of the original results nor candidate-effect estimates until the extensive effective-invalid cells are rerun.

## 4.1 Research Questions

We study three research questions. **RQ1 (effectiveness):** can Self-Harness improve task success while keeping model parameters, evaluators, and tasks fixed? **RQ2 (non-regression and transfer):** do edits proposed from Train traces transfer to tasks whose traces are hidden from the proposer without causing measurable regression? **RQ3 (model specificity):** do different models produce and retain different harness interventions rather than converging to a single generic prompt?

## 4.2 Benchmark and Splits

We use the Clean64 subset of Terminal-Bench-2.0, containing 64 terminal tasks that could be launched reliably in our environment. Before optimization, we fix a split of 43 Train tasks and 21 Heldout tasks. Train trajectories, verifier outcomes, and failure evidence are available to weakness mining and harness proposal. Heldout trajectories are hidden from the proposer and used only by the automatic promotion gate. Split assignments are identical across harness variants, and every task starts in a fresh Harbor/Docker environment.

Each harness state is evaluated with two independent attempts per task, giving 86 Train and 42 Heldout evaluation cells (128 cells per state). Across two baselines and three candidates per model, the experiment contains 1,024 scheduled evaluation cells. Infrastructure retries are not treated as additional statistical samples.

The Heldout split is hidden from proposal generation but participates in model selection through the promotion gate. We therefore interpret it as out-of-evidence validation, not as a fully independent final test set.

## 4.3 Models and Implementation

Because the original model endpoints and compute budget were unavailable, we evaluate two surrogate backends: `deepseek-v4-flash` (DeepSeek V4 Flash) and `qwen3.7-plus` (Qwen3.7 Plus). For each run, the same target model executes tasks, diagnoses failures, and proposes modifications; its weights remain fixed throughout optimization. This setup tests self-improvement of the surrounding harness rather than distillation from a stronger model.

The initial DeepAgent-based harness exposes basic file-system, editing, and shell tools. Candidate changes are restricted to declared harness surfaces, with at most one component and one file changed per candidate. We use proposal width $K=3$, at most $T=2$ evolution rounds, and two attempts per state. Harbor runs tasks in Docker with concurrency 4, an agent hard timeout of 1,800 s, and an outer timeout of 3,000 s. Experiments use Windows 11, Docker Desktop/WSL2, and Harbor 0.20.0. Credentials are read only from environment variables and are not stored in artifacts.

The current implementation first requires both baseline and candidate results to contain no unresolved infrastructure-invalid cells; otherwise acceptance stops. After this completeness check, a candidate is promoted only if it does not reduce either split and improves at least one. With $\Delta_{tr}$ and $\Delta_{ho}$ denoting changes relative to the parent harness, acceptance requires

$$
\Delta_{tr}\geq 0,\quad \Delta_{ho}\geq 0,\quad
\max(\Delta_{tr},\Delta_{ho})>0.
$$

## 4.4 Metrics and Statistical Analysis

The primary metric is Pass (%), the fraction of evaluation cells accepted by the Terminal-Bench-2.0 verifier over the final container state. To audit the already generated historical scores, the descriptive table retains their fixed-denominator convention and counts infrastructure-invalid cells as failures. The current strict gate, however, does not permit such results to determine promotion. We additionally report a sensitivity analysis restricted to cells valid under both baseline and candidate harnesses.

Validity auditing now checks not only historical `status`, but also the presence of a numeric verifier reward, absence of runtime failure, and consistency among reward, passed, and status fields. Statistics, Sealed analysis, the acceptance gate, the invalid-rerun planner, and the `result_validity` CLI now share one strict JSON-object loader: it accepts BOM-bearing files, rejects duplicate object keys at any nesting depth, and requires a root object before consuming results. Historical Clean64 auditing retains compatibility for legacy fixtures without a `reward` field; acceptance, paid reruns, paired planning, and live reporting explicitly enable strict reward mode, where a missing field is invalid. All 512 current Clean64 baseline/final cells contain `reward`, so this distinction does not change the historical counts. Task-clustered bootstrap and paired task-level permutation inference are enabled only when both baseline and candidate have zero unresolved invalid cells; when the gate is incomplete, `statistics.json` writes `null` for CI, McNemar p, and task-level permutation p and records the blocking reason, preventing downstream tools from using non-confirmatory numbers. No current comparison satisfies that prerequisite, so the table below reports historical fixed-denominator scores without confirmatory intervals or significance claims.

## 4.7 Robustness and Invalid Runs

Effective invalid cells change from 84 to 64 on Qwen Train and from 21 to 14 on Qwen Heldout. Qwen Train has no jointly valid pair and therefore no common-valid estimate. Heldout retains only 18/42 pairs, on which the observed rates are 72.22% and 88.89% (+16.67 pp); this subset is selected by infrastructure availability and cannot replace the complete paired estimate. DeepSeek retains 41 Train and 36 Heldout jointly valid cells, but its active branch did not change and therefore supplies no candidate-effect evidence.

There is therefore no complete sensitivity analysis supporting the historical direction. Confirmed promotion requires rerunning 105 effective-invalid Qwen baseline cells and 78 candidate cells and obtaining a complete zero-invalid paired result.

Repeat variability is substantial. Qwen candidate Train scores are 25.58% and 0%, while candidate Heldout scores are 71.43% and 42.86%. Two repeats are therefore insufficient for a precise estimate of absolute performance. The confirmatory path follows the source paper's two repeated attempts per candidate and prioritizes compute for the fully independent Sealed21 evaluation. A five-repeat Clean64 extension is retained as an optional precision and stability analysis rather than a prerequisite for, or substitute for, independent generalization evidence.

## 4.8 Threats to Validity

**External validity.** We evaluate two surrogate backends on Clean64 rather than the three original backends on full Terminal-Bench-2.0. The absolute scores are not a replication of the source paper, and improvement on one of two models is insufficient to establish universal cross-model effectiveness. An outcome-blind metadata audit accounts for all 89 local tasks as 64 Clean64, 21 Sealed21, and four media-capability exclusions, with zero task overlap. Difficulty is similar (total variation 0.062; hard tasks are 32.8% and 33.3%), but category composition differs substantially (total variation 0.480; Jensen–Shannon divergence 0.320 bits): data-science accounts for 23.8% of Sealed21 versus 3.1% of Clean64, and seven Clean64 categories are absent. Sealed success would therefore support generalization only to this disjoint local text-only set, not to the full Terminal-Bench category distribution or media-input tasks. See [`paper/generated/split-coverage/SPLIT_COVERAGE_AUDIT.md`](generated/split-coverage/SPLIT_COVERAGE_AUDIT.md) and [`split_coverage.svg`](generated/split-coverage/split_coverage.svg).

**Internal validity.** The Qwen baseline lacks a valid verifier outcome for 105/128 cells and the candidate for 78/128. This is not minor missingness but a systematic interruption that makes the current candidate effect unidentified. Observed confounders include API and account availability, networking, wrapper errors, and Docker scheduling.

**Implementation and backend version validity.** The confirmatory freeze hashes the runner, wrapper, bridge, analyzer, validity classifier, and byte-exact config, and records Python, Harbor, Docker, OS, Git, and execution time. Complete sorted package inventories and executable hashes for both the project and Harbor Python runtimes form a dependency bundle included in run identity. A static audit finds that all 90 `FROM` references across 89 tasks use explicit version tags, but none uses an immutable `@sha256:` digest. Dockerfiles can therefore be frozen while registry tag resolution can still drift over time. After both formal runs, a no-pull local inspection records image IDs/RepoDigests for the five Sealed21 base references; the analyzer re-parses the frozen Dockerfiles and requires the snapshot reference set to match exactly, then checks unique references, reference/resolved counts, task IDs, and `complete` consistency. Completeness is reported separately and does not alter the preregistered statistical rule. The pre-run preview currently resolves 0/5, as expected before task images are built. The launcher writes execution-plan and freeze JSON as BOM-free UTF-8, while the analyzer accepts legacy BOM-bearing JSON for backward compatibility, preventing a PowerShell/Python encoding mismatch from failing after paid execution. The remote model is likewise addressed by the provider alias `qwen3.7-plus`; a provider-side weight or inference-stack update behind that alias cannot be independently pinned or verified locally. Claims are conditional on both base-image tags and the model alias as served at execution time. See [`paper/generated/container-audit/CONTAINER_REPRODUCIBILITY_AUDIT.md`](generated/container-audit/CONTAINER_REPRODUCIBILITY_AUDIT.md).

**Selection bias.** Heldout outcomes participate in the promotion gate. Consequently, they estimate out-of-evidence validation performance rather than unbiased final generalization. A frozen, non-adaptive sealed split is required for the latter claim.

Paid execution also requires a non-blank `SELF_HARNESS_QWEN_API_KEY` in the Windows User environment; whitespace-only credentials are unavailable. The Clean64 invalid-rerun wrapper applies the same non-blank check in both foreground and detached execution paths.

**Statistical conclusion validity.** Confirmatory intervals and significance are withheld until both sides have zero invalid cells. After completion, inference will use the 43/21 tasks, two attempts per state, task-clustered bootstrap, and task-level paired permutation test. The generated `statistics.json` records this design as structured metadata: `comparison_unit=task`, `observation_unit=attempt`, repeat IDs 1/2, 20,000 task resamples with the global seed and deterministic per-model/split seed derivation, and an exact rational task-effect permutation algorithm. This prevents the prose, sample boundary, and implemented estimator from drifting apart.
